### [CRITICAL] Credenciais / segredos hardcoded (AP-01)
File: seed.py:15-21
Description: As três contas de fixture têm senha literal no código: `'1234'` (João Silva, `role: 'admin'`), `'abcd'` (Maria) e `'pass'` (Pedro) em `SEED_USERS` (`seed.py:18-20`). O comentário em `seed.py:15-16` declara a escolha como intencional ("para que os logins de dev continuem funcionando"), mas o catálogo trata senha literal de conta inicial como AP-01 mesmo quando é gravada com hash. Nenhuma das três vem de variável de ambiente e nenhuma é gerada aleatoriamente.
Impact: Qualquer pessoa com acesso ao repositório conhece a senha do usuário `admin` (`joao@email.com` / `1234`). Se o `seed.py` for executado por engano fora de desenvolvimento, cria contas administrativas com senhas públicas. Evidência de runtime: baseline #22 — `POST /login {"email":"joao@email.com","password":"1234"}` → 200 com `role: "admin"`.
Recommendation: Ler cada senha de fixture de variável de ambiente (`SEED_ADMIN_PASSWORD`, etc.) **sem fallback literal**; quando a variável não existir, gerar com `secrets.token_urlsafe()` e imprimir uma única vez na saída do script. Documentar as chaves em `.env.example`. (playbook PB-25, com PB-01)

### [CRITICAL] Endpoints de escrita sem autenticação — takeover anônimo de conta (AP-06)
File: routes/user_routes.py:19-26
File: controllers/user_controller.py:45-62
File: routes/task_routes.py:19-26
File: routes/category_routes.py:14-21
Description: `update_user` (`controllers/user_controller.py:45-62`) só chama `ensure_admin` quando o campo `role` está presente (`:57-59`). Os campos `password` (`:55-56`), `email` (`:51-54`), `name` (`:49-50`) e `active` (`:60-61`) são aceitos de qualquer requisição anônima, porque `routes/user_routes.py:24-26` não tem decorator de autenticação — passa apenas `has_admin_token()` como argumento. O mesmo vale para `POST /tasks` (`routes/task_routes.py:19-21`), `PUT /tasks/<id>` (`:24-26`), `POST /users` com `role` default (`routes/user_routes.py:19-21`), `POST /categories` (`routes/category_routes.py:14-16`) e `PUT /categories/<id>` (`:19-21`). Só os três `DELETE` e a mudança de `role` exigem `X-Admin-Token`.
Impact: **Takeover completo de qualquer conta, inclusive a de administrador, sem credencial alguma.** Evidência de runtime (`.refactor-arch/probe-server.log`): `PUT /users/1 {"password":"invadido123"}` → 200 e, em seguida, `POST /login {"email":"joao@email.com","password":"invadido123"}` → 200 com `role: "admin"`. Também confirmados anonimamente: troca de e-mail (`PUT /users/2 {"email":"atacante@evil.com"}` → 200, permite sequestro de recuperação de conta) e desativação de usuário (`PUT /users/3 {"active":false}` → 200, nega o serviço àquele usuário). No baseline, #43 (`PUT /users/4 {"name":"Ana Only"}` → 200 sem header) registra o mesmo buraco. Isso vai além de "falta auth em CRUD comum": é escalada para controle administrativo.
Recommendation: Exigir identidade autenticada em todas as rotas de escrita e autorização por proprietário/papel em `/users/<id>`: trocar senha só do próprio usuário (exigindo a senha atual) ou por admin; `email`/`active` só do próprio usuário ou por admin. Aplicar `require_auth` nas escritas de `/tasks` e `/categories`. Como o `X-Admin-Token` estático não identifica usuário, isto depende de PB-21 (token de login assinado e verificado). (playbook PB-07, com PB-21 e PB-22)

### [CRITICAL] Token de autenticação previsível e nunca verificado (AP-24)
File: controllers/user_controller.py:17, 81
Description: `POST /login` devolve `'token': LOGIN_TOKEN_PREFIX + str(user.id)` (`controllers/user_controller.py:81`), com `LOGIN_TOKEN_PREFIX = 'fake-jwt-token-'` (`:17`). O token é a concatenação de um prefixo fixo com o id do usuário: sem assinatura, sem expiração, idêntico em todo login. Nenhuma rota o verifica — `grep -rniE "headers\.get\(['\"]Authorization|jwt\.(decode|verify)|verify_token|serializer\.loads|login_required|jwt_required|before_request" --include='*.py' .` não retorna nenhuma ocorrência; a única credencial checada no projeto é o header estático `X-Admin-Token` em `middlewares/auth.py:12-18`.
Impact: Qualquer cliente forja o token de qualquer usuário (`fake-jwt-token-1` é o admin). Como nenhuma rota o lê, o login não protege nada: é um endpoint de verificação de senha cujo resultado não pode ser usado para autorizar nada — e é justamente a peça que falta para fechar AP-06 e AP-25. Evidência de runtime: baseline #22 e #23 — dois logins consecutivos devolvem exatamente `"fake-jwt-token-1"`.
Recommendation: Emitir token assinado com `SECRET_KEY` (`itsdangerous.URLSafeTimedSerializer` já disponível via Werkzeug/Flask, ou JWT) contendo id + papel + expiração, e criar um decorator `require_auth` que valide `Authorization: Bearer <token>` e popule o usuário corrente. O campo `token` continua string (shape preservado); muda só o valor. (playbook PB-21)

### [HIGH] PII listada em endpoint sem autenticação (AP-25)
File: routes/user_routes.py:9-16
File: routes/report_routes.py:13-15
File: models/user.py:24
File: services/report_service.py:102
Description: `GET /users` (`routes/user_routes.py:9-11`), `GET /users/<id>` (`:14-16`) e `GET /reports/user/<id>` (`routes/report_routes.py:13-15`) não têm nenhum decorator de autenticação e devolvem nome + e-mail de todos os usuários — `models/user.py:24` serializa `'email'` em `to_dict()` e `services/report_service.py:102` repete o campo no relatório individual. Os ids são inteiros sequenciais, então a enumeração é trivial.
Impact: Qualquer cliente anônimo extrai a lista completa de nomes, e-mails e papéis (`role`), o que alimenta phishing direcionado e identifica quais contas são administrativas. Combinado com AP-06, o atacante lê a lista de e-mails e em seguida troca a senha da conta `admin`. Evidência de runtime: baseline #10 (`GET /users` → 200 com 3 e-mails e `role`), #11 (`GET /users/1` → 200 com e-mail) e #16 (`GET /reports/user/1` → 200 com e-mail).
Recommendation: Exigir autenticação nessas três rotas (`require_auth` do PB-21); restringir `GET /users` a administradores e `GET /users/<id>` / `GET /reports/user/<id>` ao próprio usuário ou a administradores. Manter as chaves de resposta inalteradas para quem está autorizado. (playbook PB-22, com PB-21)

### [MEDIUM] Agregação em memória no relatório por usuário (AP-13)
File: services/report_service.py:89-109
Description: `user_report` carrega **todas** as tasks do usuário (`services/report_service.py:91`, via `user_service.list_user_tasks`) só para contar: laço de contagem por status em `:94-96`, `len(tasks)` em `:97`, e três varreduras adicionais em memória em `:107-109` (`overdue`, `high_priority`, `completion_rate`). Nenhuma dessas tasks entra na resposta — o endpoint devolve apenas números (`:104-109`). É o padrão que `summary_report` evita: as contagens globais usam `GROUP BY`/`outer join` (`:24-26`, `:43-49`) e o filtro de atraso vai para o SQL (`:30`).
Impact: O custo de `GET /reports/user/<id>` cresce linearmente com o número de tasks do usuário (linhas transferidas, objetos ORM materializados), para produzir 8 inteiros. Com a base de seed (4 tasks) é imperceptível; com milhares de tasks por usuário vira o endpoint mais lento da API. Inconsistência interna: duas estratégias diferentes para o mesmo cálculo no mesmo arquivo.
Impact adicional: a regra de atraso é avaliada duas vezes de formas diferentes no projeto — `task_service.overdue_filter` (SQL, `services/task_service.py:17-23`) e `Task.is_overdue` (Python, `models/task.py:53-56`).
Recommendation: Substituir por uma consulta agregada por usuário (`GROUP BY status` + `COUNT` com `CASE`, reaproveitando `task_service.overdue_filter` e `HIGH_PRIORITY_THRESHOLD`), como já é feito em `_user_productivity` (`services/report_service.py:42-59`). Resposta idêntica. (playbook PB-10)

### [MEDIUM] Validação de tipo ausente em campos de task (AP-14)
File: validators/task_validator.py:79-81, 92-93, 98-100
Description: `validate_new_task` devolve `user_id`, `category_id` e `due_date` crus (`validators/task_validator.py:79-81`) e `validate_task_update` repassa `description` sem checagem (`:92-93`) e `user_id`/`category_id`/`due_date` crus no laço de `:98-100`. `title`, `status`, `priority` e `tags` são validados por tipo; esses quatro não. O valor chega ao driver do SQLite e estoura no bind do parâmetro.
Impact: Três respostas 500 confirmadas em runtime (`.refactor-arch/probe-server.log`): `PUT /tasks/1 {"user_id":{"a":1}}` → 500 `{"error":"Erro interno do servidor"}` (log: `sqlite3.ProgrammingError: Error binding parameter 1: type 'dict' is not supported`); `PUT /tasks/1 {"description":{"x":1}}` → 500 `{"error":"Erro ao atualizar"}`; `POST /tasks {"title":"teste lista","user_id":[1]}` → 500 `{"error":"Erro ao criar task"}` (log: `Error binding parameter 5: type 'list' is not supported`). Os dois últimos são o caso mais grave: a mensagem genérica de falha de commit mascara um erro **permanente** de tipo como se fosse falha transitória de escrita, levando o cliente a tentar de novo indefinidamente. Nenhum stack trace vaza na resposta (o error handler central cobre isso), mas o status está errado: deveria ser 400.
Recommendation: Validar `user_id`/`category_id` como inteiros positivos (reutilizando `validators/common.py:19-26` ou `is_number`), `due_date` como string antes de `parse_due_date`, e `description` como string ou `None`, lançando `ValidationError` → 400. (playbook PB-11)

### [MEDIUM] Fonte de data divergente em /health (AP-15)
File: routes/system_routes.py:1, 13
File: utils/helpers.py:5-7
Description: `GET /health` monta o timestamp com `datetime.datetime.now()` (`routes/system_routes.py:13`, com `import datetime` em `:1`) — hora **local** do servidor. Todo o resto da API usa o helper único `utils.helpers.utcnow()` (`utils/helpers.py:5-7`, `datetime.now(timezone.utc)` sem tzinfo), inclusive os defaults das colunas (`models/task.py:16-17`, `models/user.py:17`, `models/category.py:13`) e `generated_at` do relatório (`services/report_service.py:63`). O helper existe e não é chamado nessa rota; nenhum campo carrega offset de fuso.
Impact: Dois campos de timestamp da mesma API, ambos sem fuso declarado, em escalas diferentes. Evidência de runtime: baseline #2 — `GET /health` → `"timestamp":"2026-11-14 11:56:25"` contra `created_at":"2026-11-14 14:56:16"` da mesma execução (#3): 3 horas de defasagem. Um cliente que use `/health` como referência de relógio para calcular atrasos erra por um fuso inteiro; em servidor com `TZ=UTC` a diferença desaparece silenciosamente, o que torna o bug dependente de ambiente.
Recommendation: Usar `utils.helpers.utcnow()` em `routes/system_routes.py:13`. **Atenção:** isso altera um valor observável da resposta (não a chave nem o tipo), logo é mudança de contrato que precisa de aprovação explícita; se o valor em hora local tiver de ser preservado, documente-o no README e no `.env.example` em vez de corrigir. (playbook PB-18, com PB-24 para a documentação)
